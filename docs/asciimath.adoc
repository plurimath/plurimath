= AsciiMath in Plurimath
:toc:

This page specifies the AsciiMath that Plurimath reads and writes: where the
grammar comes from, the whitespace and number rules, how terms group, the
symbol and operator vocabulary, the uncertainty call forms, the errors, and
the corpora that check all of this. It is part of the specification set
tracked in https://github.com/plurimath/plurimath/issues/525[#525].

The grammar and vocabulary excerpts on this page are generated from the amath
grammar artifact and checked against its recorded checksums (see
<<regenerating>>). Everything else describes behaviour of the code at the
revisions named in <<source-of-truth>>.

The measurement model behind `ustd`, `uexp` and `ucov`, and how it is carried
in the other formats, is in link:uncertainty.adoc[Measurement uncertainty].

[[source-of-truth]]
== Grammar source of truth

Plurimath has no AsciiMath grammar of its own. `Plurimath::Asciimath::Parser`
calls `Amath.parse(text, dialect: :legacy, engine: :ruby, decimal:
Plurimath.configuration.decimal)`, and `Plurimath::Asciimath::Mapper` turns
the returned typed model (`Amath::Model::Document`) into a Formula with the
rule table `Plurimath::Asciimath::Mapper::Rules`. The `:pma` input type
goes through the same parser and mapper with `dialect: :pma`
(link:pma.adoc#selection[pma selection]); `:asciimath` is always dialect L.
`Plurimath::Asciimath::Parse` stays as a tree-level entry point that returns
amath's internal legacy-shaped raw tree; Plurimath's own parsing does not use
it. The grammar is
the amath PARG artifact `artifacts/asciimath.json`, compiled by Parsanol from
`grammars/asciimath.parg`. That file is itself generated from
`grammars/asciimath.parg.template` and `data/vocabulary.json`, which amath
exports once from a pinned Plurimath revision. amath's own contracts are
`docs/parser-contract.adoc` (the typed-model API that Plurimath uses) and
`docs/stage-contract.adoc` (the shared profile for the stage gems).

Before the grammar runs, `Plurimath::Asciimath::Parser` replaces the bracket
digraphs `|:` and `:|` by `|`, `{:` by U+2112, `:}` by U+211B, `(:` by U+1455
and `:)` by U+1450. Those four code points are the invisible-bracket
characters the grammar matches.

Plurimath runs the released amath gem, pinned to `+~> 0.1.0+`. The documented
amath revision below may be newer than the released gem. The table records
both, and the generator refuses to run unless the uncertainty rules of the
two are byte-identical. The grammars differ only in the entry rule: newer
revisions wrap the whole tree in one `root` capture for the typed-model
bindings, which amath removes before returning the tree.

== Whitespace and numbers

The lexical rules, quoted from the grammar for the `dot` entry (the `comma`
and `arabic` entries differ only in the decimal marker):

// BEGIN GENERATED lexical-grammar
[source]
----
space = " " / "\t" / "\n" / "\r" / %x0B / %x0C
space_opt = [space]
comma = "," space_opt
digit = %x30-39
decimal_marker__dot = "."
decimal_number__dot = (1*digit decimal_marker__dot 1*digit) / 1*digit
number__dot = hex_number / binary_number / octal_number / (decimal_number__dot) as number / (".") as symbol
signed_number__dot = ("-" decimal_operand__dot) as number
hex_number = ("0x" / "0X") ((1*(%x30-39 / %x41-46 / %x61-66)) as hex_number)
binary_number = ("0b" / "0B") ((1*(%x30-31)) as binary_number)
octal_number = ("0o" / "0O") ((1*(%x30-37)) as octal_number)
base = !"__|" "_"
power = "^"
frac_slash = "/" !"/"
quoted_text = ("\"" "unitsml(" (*(!")\"" any_char)) as unitsml ")\"") / ("\"" (*(!"\"" any_char)) as text "\"") / ("\"" "" as text)
----
// END GENERATED lexical-grammar

Whitespace::
`space` is exactly one character of space, tab, line feed, carriage return,
vertical tab or form feed. Outside the uncertainty calls, whitespace between
terms is consumed one character at a time, so runs of any length are allowed
and do not change the result: `x  +  y` reads the same as `x + y`. The
AsciiMath writer emits its own spacing.

Whitespace inside uncertainty calls::
Inside `ustd(`, `uexp(` and `ucov(`, any amount of whitespace may stand after
the opening bracket, around each comma and before the closing bracket. No
whitespace may stand between the word and its bracket (`ustd (1.2, 0.1)` is
the letters `u s t d` followed by a bracketed group), or before the `e` of a
shared exponent.

Numbers::
A number is digits with an optional single decimal marker followed by more
digits, or a `0x`, `0b` or `0o` prefixed integer. The decimal marker is the
one selected by the parse locale (see <<locale>>); there is no exponent
syntax outside the uncertainty calls, so `1.2e3` is the number `1.2`, the
letter `e` and the number `3`.

[[precedence]]
== Precedence and grouping

AsciiMath has no operator precedence table in the usual sense: `+`, `-`, `=`
and the other operators are symbols in a flat sequence. Only a few
constructions take operands, and they bind in this order, tightest first:

. Brackets, `+text(...)+`, quoted text and the function words with their
  arguments (`sqrt x`, `frac a b`, `root 3 x`, `+sum_(i=1)^n+`).
. Subscript `_` and superscript `+^+`. Both may follow the same base, in either
  order (`+a_b^c+`, `+a^b_c+`). A second `+^+` after a superscript is a new
  superscript on the result (`+x^2^3+`).
. Fraction `/`. A fraction takes the preceding script expression or bracket
  as its numerator and the rest of the following operand as its denominator,
  so it groups to the right: `1/2/3` is `1/(2/3)`, and `+a/b^2+` is
  `+a/(b^2)+`. A function word stays in the numerator: `sqrt x/y` is
  `(sqrt x)/y`. `//` is the slash symbol, not a fraction.
. `mod`, whose divisor may itself be a fraction (`a mod b/c` is
  `a mod (b/c)`), while a fraction's denominator may hold a `mod`
  (`a/b mod c` is `a/(b mod c)`).
. Everything else is a left-to-right sequence. `a+b/c+d` is `a`, `+`,
  `b/c`, `+`, `d`. A leading `-` is a symbol, so `-a/b` is `-` followed by
  `a/b`.

An uncertainty call is an ordinary operand: `ustd(1.2, 0.1)/2` is a fraction
whose numerator is the uncertainty, and `+ustd(1.2, 0.1)^2+` puts a superscript
on it.

These groupings follow from the order of the alternatives in the grammar
rules `iteration`, `frac`, `mod` and `power_base`; the corpus groups `frac`,
`mod`, `powers` and `operators` (see <<conformance>>) pin them.

[[uncertainty]]
== Uncertainty call forms

The three words `ustd`, `uexp` and `ucov` start a call that reads as one
`Plurimath::Math::Function::Uncertainty` node. The normative rules, quoted
from the grammar:

// BEGIN GENERATED uncertainty-grammar
[source]
----
unc_number = 1*digit ["." 1*digit]
unc_value = (["-"] unc_number) as value
unc_sep = *space "," *space
unc_unit = unc_sep "\"unitsml(" (*(!")\"" any_char)) as unit ")\""
unc_open = "(" *space
unc_close = *space ")"
unc_shared_exponent = "e" (["+" / "-"] 1*digit) as shared_exponent
unc_measured_pair = unc_value unc_sep (unc_number) as magnitude
unc_scaled_pair = unc_open unc_measured_pair unc_close unc_shared_exponent
unc_measured_interval = unc_value unc_sep (unc_number) as lower unc_sep (unc_number) as upper
unc_scaled_interval = unc_open unc_measured_interval unc_close unc_shared_exponent
unc_standard = unc_scaled_pair / unc_value (unc_sep (unc_number) as magnitude / "(" (1*digit) as concise_digits ")" [unc_shared_exponent])
uncertainty = (uncertainty_std / uncertainty_exp / uncertainty_cov) as uncertainty
uncertainty_std = ("ustd") as uncertainty_class unc_open unc_standard [unc_unit] unc_close
uncertainty_exp = ("uexp") as uncertainty_class unc_open (unc_scaled_pair / unc_measured_pair) unc_sep (unc_number) as coverage_factor [unc_sep (unc_number) as coverage_probability] [unc_unit] unc_close
uncertainty_cov = ("ucov") as uncertainty_class unc_open (unc_scaled_interval / unc_measured_interval) unc_sep (unc_number) as coverage_probability [unc_sep ("shortest" / "symmetric") as interval_kind] [unc_unit] unc_close
----

Checksum of the excerpt (lines joined by line feeds): `sha256:4ff5df3b0613419404fdfc9db0949439c4600cd392f0773b958f9800d349d0d9`.
// END GENERATED uncertainty-grammar

The forms they accept:

[cols="2,3"]
|===
|Form |Meaning

|`ustd(y, u)`
|standard uncertainty, absolute notation

|`ustd(y(d))`
|standard uncertainty, concise notation: `ustd(1.230(4))` means `u = 0.004`

|`uexp(y, U, k)`, `uexp(y, U, k, p)`
|expanded uncertainty with coverage factor `k` and optional coverage
probability `p`

|`ucov(y, lo, hi, p)`, `ucov(y, lo, hi, p, shortest)`, `ucov(y, lo, hi, p, symmetric)`
|coverage interval with its endpoints, coverage probability and optional
interval choice; `symmetric` is the probabilistically symmetric interval

|any of the above with a last argument `+"unitsml(...)"+`
|the same result with a UnitsML unit, for example
`uexp(100.02147, 0.00079, 2, "unitsml(g)")`
|===

Only the value `y` may carry a minus sign. Every number uses a full stop as
its decimal marker and has no exponent of its own. The interval choice is
written `symmetric` because AsciiMath would read the `-` of
`probabilistically-symmetric` as minus. The numbers are kept as written:
`1.230` stays `1.230`, and no floating-point value is computed.

=== Shared exponents

The measured fields may be grouped and followed by `e` and a signed or
unsigned integer, which applies to the value and the magnitude, or to the
value and both endpoints. Coverage factors and probabilities are not scaled.

[cols="2,2"]
|===
|Input |Written back

|`ustd((3.85, 0.23)e4)` |`ustd(38500, 2300)`
|`ustd(680(41)e-3)` |`ustd(0.680(41))`
|`uexp((3.85, 0.23)e+4, 2, 0.95)` |`uexp(38500, 2300, 2, 0.95)`
|`ucov((1.024, 0.983, 1.088)e-3, 0.95, shortest)` |`ucov(0.001024, 0.000983, 0.001088, 0.95, shortest)`
|===

The shift is done on the decimal text. For concise notation the magnitude is
derived from the value's decimal places before the shift. A shift that would
make a number longer than 1,000,000 characters is rejected. The writer emits
the shifted numbers, not the exponent.

=== When a call is not an uncertainty

A call that does not match these rules is not an error. The grammar falls back
to the reading it had before the words existed, letter by letter
(amath#9):

* `uexp(10.0, 0.3)` (no `k`) is `u` followed by `exp(10.0, 0.3)`;
* `ustd(1.2, -0.1)`, `ustd(1.2e3, 0.1)`, `ustd (1.2, 0.1)` and
  `ustd((3.85, 0.23) e4)` are the letters `u s t d` followed by a bracketed
  group;
* `+-` and `pm` are always the plus-minus symbol (`Math::Symbols::Pm`), a
  literal `±` is an ordinary symbol, and `1.230(4)` outside a call is a number
  followed by a bracketed group. None of them starts an uncertainty.

A call that matches the rules but whose numbers are not a valid result, such
as `uexp(1.0, 0.3, 0, 0.95)` (`k` must be greater than 0) or
`ucov(1.0, 2.0, 1.5, 0.95)` (the lower endpoint is above the upper one), is an
error (see <<errors>>).

The parse tree each form produces, before Plurimath turns it into a node, is
recorded in link:uncertainty-asciimath-tree.md[the AsciiMath uncertainty tree
contract].

[[locale]]
=== Locale and decimal commas

`+Plurimath::Math.parse(text, :asciimath, locale: ...)+` selects the decimal
marker for ordinary numbers: amath has one artifact entry per marker (`dot`,
`comma` and `arabic`). Inside an uncertainty call the marker is always a full
stop and the argument separator is always a comma.

Under a locale whose decimal marker is not a full stop, a call in which a
separator comma is directly followed by a digit, such as `ustd(1,5)` or
`ustd(1.2,0.1)` under `locale: :fr`, raises
`Plurimath::Math::AmbiguousDecimalError` instead of guessing.
`ustd(1.230, 0.004)`, with a space after each comma, reads the same under every
locale. Calls inside quoted text are not checked. A value written with the
Arabic decimal mark, such as `ustd(1٫230, 0٫004)` under `locale: :ar`, is not
an uncertainty call and reads as letters followed by a bracketed group.

[[errors]]
== Errors

`Plurimath::Math.parse(text, :asciimath)` raises these errors. All of them are
`Plurimath::Math::ParseError`, which is a `Plurimath::Error`.

[cols="2,3"]
|===
|Error |Raised when

|`Plurimath::Math::ParseError`
|amath rejects the input (`Amath::ParseError`, including
`Amath::NestingTooDeep` for input nested too deeply for the engine), or the
transform cannot build a node from the tree. An uncertainty call whose
numbers fail validation is reported this way: the
`Plurimath::Errors::InvalidUncertainty` raised inside is not kept as the
`cause`.

|`Plurimath::Math::AmbiguousDecimalError` (a `ParseError`)
|a call has a likely decimal comma under a non-dot locale (<<locale>>). It is
raised before amath runs and reaches the caller unchanged.

|`Plurimath::Math::MissingDependencyError` (a `ParseError`)
|the amath gem cannot be loaded.
|===

Building the node directly, with `Plurimath::Math::Function::Uncertainty.new`,
raises `Plurimath::Errors::InvalidUncertainty` (a `Plurimath::Error`, not a
`ParseError`) for any field that does not form a valid result. Unknown parse
options raise `Plurimath::Errors::ParseOptionError`, and an unknown format
name raises `Plurimath::Math::InvalidTypeError`.

amath's own error classes (`Amath::ParseError` with `byte_offset` and
`char_offset`, `Amath::NestingTooDeep`, `Amath::ArtifactError`,
`Amath::EngineUnavailable`) are specified in amath's
`docs/parser-contract.adoc`. Plurimath turns an amath rejection into a
`Parslet::ParseFailed` positioned at amath's byte offset before
`Plurimath::Math.parse` reports it.

[[conformance]]
== Conformance

These corpora and fixtures check the behaviour on this page:

* plurimath-testsuite, `stages/asciimath/generations/000001/payloads/`, layout
  revision 1 (plurimath-testsuite `6f8bc12`). Its 28 groups, with 173 rows,
  cover numbers, whitespace, symbols, operators, fractions, `mod`, powers,
  roots, fonts, matrices, brackets, quoted text, UnitsML, number formatting
  and rejections. Generation 1 is a byte copy of `corpus/asciimath/` at
  plurimath-testsuite `281059b`, which is the commit of Plurimath's
  `submodules/plurimath-testsuite`; Plurimath replays it with
  `scripts/replay_asciimath_corpus.rb` and
  `spec/plurimath/asciimath_corpus_replay_spec.rb`.
* amath `corpora/uncertainty-shared-exponent.yml`: the input, tree and exact
  decimal expectation for every shared-exponent form, checked by amath's
  specs and by `spec/plurimath/asciimath/uncertainty_shared_exponent_spec.rb`.
* Plurimath `spec/plurimath/fixtures/uncertainty/contract.yml`: the exact
  output of every uncertainty form in every format, its invalid cases, and the
  ordinary `±` cases, checked by `spec/plurimath/uncertainty_contract_spec.rb`
  and `spec/plurimath/asciimath/uncertainty_spec.rb`.
* `spec/plurimath/asciimath/uncertainty_locale_spec.rb` and
  `spec/plurimath/asciimath/uncertainty_contexts_spec.rb`: the locale rule and
  uncertainty calls inside other constructions.

The testsuite has no uncertainty rows yet. They are expected as a later
asciimath generation, appended under the stage layout of
https://github.com/plurimath/plurimath/issues/540[#540].

== Regenerating this page

The regions between `// BEGIN GENERATED` and `// END GENERATED` comments are
written by `scripts/docs/asciimath_tables.rb`. Do not edit them by hand. To
update them after an amath change, check out amath at the revision to
document and run, from the Plurimath checkout:

[source,sh]
----
bundle exec ruby scripts/docs/asciimath_tables.rb --amath ../amath

The script checks `grammars/asciimath.parg` and `data/vocabulary.json`
against `artifacts/asciimath.checksums.txt` in that checkout, and compares the
uncertainty rules with the artifact of the amath gem the bundle loads. It
stops without writing anything when either check fails. Add `--check` to
verify that this page is current without changing it; it then exits 1 when the
page is out of date.
