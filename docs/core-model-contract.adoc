= Core model contract
:toc:

This document scopes
https://github.com/plurimath/plurimath/issues/337[#337], the migration of
the Plurimath formula tree to lutaml-model. It lists what is left to
migrate, the order the migration follows, how each step proves it changed
nothing, and the risks and dependencies. Its roadmap position and definition
of done are in https://github.com/plurimath/plurimath/issues/541[#541].

`main` at `70c3384d`, before

== Scope

After the stage gems are extracted, only the shared core is left to migrate:
`Plurimath::Math::Formula`, the `Plurimath::Math::Function` classes, `Core`,
`Number`, the symbol classes and the uncertainty and UnitsML nodes. The stage
gems (`amath`, `latexmath`, `unicodemath`) define their own models in
lutaml-model from the start, so none of their classes appear here.

The migration follows three rules from the #541 definition of done and from
https://github.com/lutaml/lutaml-model/issues/1033[lutaml-model#1033]:

* The core tree is defined with lutaml-model. Hand-written field
  declarations (`attr_accessor` and the constructors that fill them) are
  generated or replaced by lutaml-model attributes.
* lutaml-model carries the data and the per-format writers stay in Ruby.
  The writer methods (`to_asciimath`, `to_latex`,
  `to_mathml_without_math_tag`, `to_omml_without_math_tag`,
  `to_unicodemath`, `to_html`) and everything they call are not moved into
  lutaml-model mappings.
* The public API does not change, and the bytes every writer produces over
  the corpora do not change.

The following are out of scope:

* The stage gems' models and the mapping from them into the core tree. That
  mapping belongs to #531.
* The symbol catalog data, meaning the `INPUT` spelling tables and the
  per-symbol writer bodies. They are staged separately under
  https://github.com/plurimath/plurimath/issues/537[#537]. This migration
  only declares the fields of the symbol base classes.
* The support classes under `Plurimath::Math` that are not tree nodes, such
  as the evaluator, the semantic tree view and the error classes.

== Inventory

=== Regenerating

The tables marked as generated are written by
`scripts/docs/core_inventory.rb`. Do not edit them by hand. To refresh them
from the checked-out revision, run:

[source,sh]
----
bundle exec ruby scripts/docs/core_inventory.rb
----

With `--check` the script writes nothing and exits 1 when the generated
regions are out of date. The output depends only on the source tree.

The script loads Plurimath, requires every file under `lib/plurimath/math`
and lists every class whose name starts with `Plurimath::Math::`. For each
class it reads:

* the fields, meaning methods created by `attr_accessor`, `attr_reader` or
  `attr_writer`, and the class that declares them;
* the class that defines `#initialize`, with its parameters and default
  expressions copied from the source;
* the public methods the class defines itself, without the field methods;
* which of the six writers the class responds to.

=== Marks

Each class gets one mark:

stays-core:: A tree node that carries at least one writer, plus the abstract
root `Core`. It is used by the writers and by the shared tree, so it stays
in Plurimath after #531 and is migrated by #337.
removed-by-531:: A tree node with no writer at all. It cannot reach any
output, so it would only exist for the in-tree LaTeX and UnicodeMath
parsers, and #531 removes it.
support:: A class under `Plurimath::Math` that is not a tree node. It is not
migrated.

On this snapshot no class is marked removed-by-531. The in-tree LaTeX and
UnicodeMath parsers live outside `Plurimath::Math`, under
`lib/plurimath/latex/` and `lib/plurimath/unicode_math/`, and every class
they build is also written by the writers. #531 keeps all of these classes,
because the stage-gem mappings must build the same trees for the writer
output to stay byte-identical. What #531 can remove inside `Plurimath::Math`
is listed in <<parser-only>>.

Three things in this table shape the migration:

* Field ownership is not limited to the five Function bases. 27 leaf
  classes declare one more field of their own: `attributes` (accent
  classes such as `Hat` and `Vec`), `options` (`Frac`, `Sum`, `Int` and
  others) or `open_paren` and `close_paren` (`Abs`, `Ceil`, `Floor`,
  `Norm`).
* Some leaf classes only override the constructor to change a default, such
  as the `FontStyle` and `Table` subclasses. The defaults are part of the
  public API and stay as they are.
* `Uncertainty` uses keyword arguments and read-only fields, and `Unitsml`
  keeps a derived value (the parsed UnitsML) next to its one field.

== Migration plan

=== Order

The migration goes through the field-owning classes in a fixed order, from
the leaves of the tree to its root. Each step is one pull request, and a step
starts only after the previous one is merged with full CI at its exact head.

[cols="1,3,3",options="header"]
|===
| Step | Declares in lutaml-model | Why here

| F2
| `Core` becomes the lutaml-model root of the tree. `Number`,
  `Symbols::Symbol` and `Symbols::Paren` declare their fields.
| These hold only strings, booleans and option hashes, never other nodes, so
  nothing in them is recursive. One base covers all symbol classes.

| F2a
| The common Function owners: `UnaryFunction`, `BinaryFunction`,
  `TernaryFunction`, `Nary` and `Table`.
| Their `parameter_*` and `value` fields hold other nodes, so this is where
  the tree becomes recursive (see <<risks>>).

| Further cards
| The leaf classes that add their own field (`attributes`, `options`,
  `open_paren` and `close_paren`), then `Uncertainty` and `Unitsml`.
| Each is cut as its own card from the bases table above before F3. They
  depend on the F2a bases.

| F2b
| `Formula`, `Formula::Mrow` and `Formula::Mstyle`: the `value` collection
  and the display fields.
| `Formula` is the container every reader returns and every writer starts
  from, so it goes last.

| F3
| Nothing new. It checks that every stays-core class in the regenerated
  inventory has its fields declared in lutaml-model, directly or through a
  base, and that the API and byte baselines still match.
| Closes the #337 definition of done.
|===

=== What each step declares and what stays Ruby

Each step declares, in lutaml-model, the fields of the classes it migrates:
name, type, whether it is a collection, and the default. The field names do
not change.

The following stay hand-written Ruby:

* Every writer method and the helpers they call. These are almost all of the
  "Own public methods" column.
* The constructors. Their positional and keyword parameters and defaults are
  public API (see the bases table), so each migrated class keeps an
  `initialize` that accepts the same arguments and fills the declared
  attributes. lutaml-model#1033 already plans to export such classes with a
  custom-initialize marker rather than reject them.
* `==` on every class, and the per-class normalisation in setters such as
  `Symbol#value=`.
* The no-op `element_order=` on `Number` and `Function::Text`, and
  `Core#pretty_print_instance_variables`. These are the only public method
  names a node shares with `Lutaml::Model::Serializable` on 0.8.164. The
  Plurimath definitions keep precedence.

lutaml-model also adds its own public methods (85 on 0.8.164, such as
`to_hash` and `to_yaml`) to every node. This adds to the API and changes no
existing method, and each step's API check records it.

=== Byte and API baseline

Before F2 starts, on the `main` revision it branches from, the following are
recorded. Every later step compares against them at its exact head.

* *Writer bytes:* for every input in the shared corpus at the pinned
  testsuite generation (922 cases in the snapshot above, 780 to 782 per
  target), parse it with its reader and write it with all six writers, with
  the call options the corpus records. This runs once per XML engine (Ox, Oga
  and Leptris, as `spec_helper` does). The result is one digest per engine
  and target over the whole corpus, kept with the outputs so that a mismatch
  points to the case. The shared conformance suite already checks the Ox
  bytes on every pull request. The other two engines are covered by this
  baseline and by the full suite in GHA.
* *Field types:* over the same parses, the class of every value each field
  holds. Each step picks its lutaml-model attribute types from this list,
  not from reading the code.
* *API:* the generated tables in this document, meaning constructor
  signatures and defaults, fields and own public methods. Each step
  regenerates them and the diff may only show the migrated declarations
  moving into lutaml-model and the methods lutaml-model adds.

The full suite and the shared conformance suite run in GHA on every step.
They are not run locally.

=== Stop rule

A step stops and reports, rather than working around the problem, when a
class does not fit:

* a field holds more than one kind of value that lutaml-model cannot declare
  without a union type (`Lml.export` rejects unions on 0.8.x), such as a
  field that holds either a node or a plain string;
* a constructor or default cannot be kept byte-for-byte and API-for-API;
* any baseline digest changes;
* a class needs a change in lutaml-model itself. That work belongs to the
  lutaml-model maintainers and is out of scope here.

The report names the class, the field and the failing check, and the class
stays hand-written until a separate card settles it. The migration does not
change writers, the symbol vocabulary or reader transforms to make a class
fit.

[[risks]]
== Risks and dependencies

=== lutaml-model serialization of recursive models

On lutaml-model 0.8.162, `to_hash` and `to_yaml` never finished on the
recursive stage-gem models. The amath and UnicodeMath model work found this.
Building the models and exporting their declarations worked. The cost
appears to come from the key-value transformation being rebuilt for every
attribute type it reaches, with no memo, so it grows with the cycles in the
declared type graph and not with the size of the value.

A probe on 0.8.164 shows the same growth. With N classes that each declare
an attribute of every other class, `to_hash` of a two-node value took
0.08 s for N=2, 0.78 s for N=6 and 54 s for N=8. The core tree is a worst
case for this, because almost any node can hold any other node.

The `unicodemath` gem works around it with shared hub classes. Node slots
are typed by a few hub classes instead of one class per capture, and its
generator checks that the declared type graph has no cycle outside the
hubs. In the same probe, with one hub class and N classes whose only node
slot is a collection of the hub, `to_hash` took 0.13 s for N=8 and 0.41 s for
N=120.

For this migration that means:

* Node-valued fields (`parameter_*`, `value`, `open_paren`, `close_paren`)
  are typed by one hub, the abstract `Core`. No other class may appear as an
  attribute type of another node class. F2a adds the same no-cycle check as
  `unicodemath`.
* Whether lutaml-model serializes a subclass instance held in a hub-typed
  field with all of that subclass's fields must be shown in F2a. If it
  cannot without a union or polymorphic declaration, the stop rule applies.
* Plurimath does not call `to_hash` or `to_yaml` on the tree today, so the
  bug blocks no existing path. It blocks any new serialization of the core
  tree until it is fixed in lutaml-model or the hub layout avoids it.

=== Symbol catalog size

The symbol classes are 1,461 of the 1,602 classes. They are declared through
their two base classes, so the migration does not touch each one. Their
spelling tables, per-symbol writer bodies and load cost are #537's staged
symbol catalog. If #537 moves the catalog to data before F2, the symbol rows
of the inventory change and the F2 scope shrinks to the two bases.

=== The three-engine spec loop

`spec_helper` runs every example on Ox, Oga and Leptris. The full suite took
1273 s on the fixed runner in the performance baseline
(`docs/performance-contract.adoc`). Each migration step needs a full run at
its exact head, so the steps are bounded by GHA time, not by local runs. #537
moves the engine loop into the per-stage suites. Until then the loop stays,
and the byte baseline above is taken on all three engines for the same
reason.

=== Order relative to #531

* This scope is finalised only after #531 lands. #531 removes
  `lib/plurimath/latex/` and `lib/plurimath/unicode_math/` and may remove the
  parser-only surfaces listed above. F2 then branches from post-#531 `main`.
* The byte baseline is taken after #531 and after any open change to writer
  output, such as the UnicodeMath writer fix for multi-letter units, so that
  it records the bytes the migration must keep.
* F2 also waits for the model-ownership decision the plan records as O2.
* lutaml-model#1033 (the declaration exporter) is a dependency for
  exporting and checking the migrated declarations, not for declaring them.
