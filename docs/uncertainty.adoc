= Measurement uncertainty
:toc:

Plurimath represents a reported measurement result, such as `100.02147(35)` or
`(10.0 ± 0.3), k = 2`, as one node,
`Plurimath::Math::Function::Uncertainty`, and reads and writes it in every
format it supports. This page specifies that node, the marker each format
uses to carry it, what survives a round trip, and the decisions that are still
open. It is part of the specification set tracked in
https://github.com/plurimath/plurimath/issues/525[#525]; the AsciiMath call
forms are specified in full in link:asciimath.adoc[AsciiMath in Plurimath].

Section numbers refer to JCGM 100:2008 (the GUM) unless marked JCGM 101:2008.

== Scope

Plurimath records and converts a reported result. It does not calculate
anything: no uncertainty propagation, no combination, no conversion between
`U`, `k`, `p` and `u`, no rounding and no unit conversion. Evaluation with
uncertainty is a separate requirement set,
https://github.com/plurimath/plurimath/issues/514[#514].

AsciiMath, MathML, OMML and UnicodeMath are read and written. LaTeX and HTML
are written only.

An ordinary plus-minus sign keeps its meaning. A measurement is recognised only
from the explicit forms in <<markers>>.

[[model]]
== The model

[source,ruby]
----
Plurimath::Math::Function::Uncertainty.new(
  value,                       # Math::Number, the measured value y
  category:,                   # :standard, :expanded or :coverage_interval
  magnitude: nil,              # Math::Number, u or U
  coverage_factor: nil,        # Math::Number, k
  coverage_probability: nil,   # Math::Number, p
  lower: nil, upper: nil,      # Math::Number, interval endpoints
  interval_kind: nil,          # :shortest, :probabilistically_symmetric or nil
  notation: :absolute,         # :absolute or :concise (standard only)
  unit: nil,                   # Math::Function::Unitsml, or Math::Formula when read from markup
)
----

=== The three categories

Standard uncertainty (§7.2.1, §7.2.2)::
A value `y` and its standard uncertainty `u`, an absolute, nonnegative number
in the unit of `y`. It takes no coverage factor and no coverage probability:
§7.2.2 (note) warns that reading `u` as an interval with a level of confidence
is usually not justified.

Expanded uncertainty (§6.2.1, §6.3, §7.2.3, §7.2.4)::
A value `y`, a symmetric expanded uncertainty `U` and the coverage factor `k`
that was used. `k` is required: §7.2.3 (4) asks for it, and without it the
result could not be told apart from an ordinary `±`. The coverage probability
`p` is optional and only recorded when given. Plurimath never derives `p`
from `k` or the reverse (§6.3.2, §6.3.3).

Coverage interval (JCGM 101 §5.3, §5.5)::
A value `y`, the lower and upper endpoints of the interval (not distances from
`y`), the required coverage probability `p`, and optionally which interval was
chosen: the shortest (§5.3.4) or the probabilistically symmetric (§5.3.3).
`k` is not accepted. `y` need not lie between the endpoints, because
§5.3.4 only says the shortest interval contains the mode.

=== Exact decimal text

Every number is a `Math::Number` whose text is a plain decimal,
`-?[0-9]+(\.[0-9]+)?`. Only `value` may be negative. No exponent, no comma or
other decimal marker, no `base`, and no mini-sized digits. The text is kept as
given, so `1.230` stays `1.230`, and no `Float` is ever made. Range checks
compare the decimal text exactly. Writers print the text as stored: the
configured number formatter and locale are not applied, so output never
re-rounds a value or changes its decimal marker.

=== Validation

The constructor raises `Plurimath::Errors::InvalidUncertainty` (a
`Plurimath::Error`) unless:

* `u` and `U` are at least 0, `k` is greater than 0, and `p` lies strictly
  between 0 and 1 (`0.95`, not `95`);
* `lower` is below `upper`;
* the fields that do not belong to the category are `nil` (for example `k` on
  a standard result), and the required ones are present;
* `notation` is `:absolute` or `:concise`, and is given only for a standard
  result;
* a `:concise` result has a magnitude with exactly as many decimal places as
  the value;
* `unit` is `nil`, a `Math::Function::Unitsml`, or a non-empty
  `Math::Formula` that holds no other uncertainty.

=== Notations

§7.2.2 lists four ways to write a standard uncertainty. Two of them are
`notation` values:

* `:absolute` (form 3), `100.02147(0.00035)`: the number in brackets is the
  uncertainty itself. This is the default.
* `:concise` (form 2), `100.02147(35)`: the digits in brackets apply to the
  last digits of the value.

The model always stores the absolute magnitude. The two convert by moving the
decimal point in the text: `1.23(4)` means `u = 0.04` and `1.230(4)` means
`u = 0.004`. A magnitude that does not have the value's number of decimal
places, such as `0.004` after `1.2`, cannot be concise. Form 4, `(y ± u)`, is
not offered for a standard uncertainty, because the §7.2.2 note says to avoid
it; `±` is written only for an expanded result, always with `k`.

=== Equality and copies

`==` compares the class and every field, including `notation` and the exact
number text. `ustd(1.23(4))` and `ustd(1.23, 0.04)` hold the same magnitude
but are not equal. A copy made with `cloned_objects` goes through the
constructor, is `==` to the original and shares no child objects. Line
breaking never splits the node.

[[units]]
=== Units

The optional unit follows §7.2.1 (2) and §7.2.3 (2), which ask for the unit
to be given, and §7.2.4, which places it after the bracketed result and before
the coverage statement: `(100.02147 ± 0.00079) g, k = 2`.

* A unit built from AsciiMath or in code is a `Math::Function::Unitsml` and
  keeps its UnitsML text.
* A unit read from MathML, OMML or UnicodeMath is the rendered content, a
  `Math::Formula`. Plurimath does not turn rendered markup back into UnitsML,
  as for every other UnitsML node.
* When writing AsciiMath, a `Math::Formula` unit is written back as
  `+"unitsml(...)"+` when it is a `·`-separated product of upright ASCII-letter
  symbols with optional integer powers, and UnitsML renders that text back to
  the same product. `kg`, `+m^2+` and `+s^-1+` qualify. `µm` and `°C` do not, and
  are written after the call in their AsciiMath form, for example
  `+ustd(1.2, 0.1) rm(&#xb5;m)+`, which reads back as an uncertainty without a
  unit followed by the unit expression.
* A UnitsML text that the installed UnitsML version cannot read is rendered as
  `+rm(...)+` (#516).

[[markers]]
== Marker grammars

=== The marker string

MathML, OMML and UnicodeMath carry the whole result in one marker string,
written in MathML 4 intent syntax with literal numbers. The marker is
authoritative: on reading, only the marker and the unit are used, and the
visible content is regenerated on output.

[source]
----
marker      = S name [S ":" property] S "(" arguments ")" S
name        = "standard-uncertainty" | "expanded-uncertainty" | "coverage-interval"
arguments   = S number S *("," S number S) ["," S "$unit" S]
number      = ["-"] 1*digit ["." 1*digit]
----

[cols="1,2,2"]
|===
|Category |Marker |Property

|standard
|`standard-uncertainty(y,u)`
|none (absolute) or `concise`

|expanded
|`expanded-uncertainty(y,U,k)`, `expanded-uncertainty(y,U,k,p)`
|none

|coverage interval
|`coverage-interval(y,lo,hi,p)`
|none, `shortest` or `probabilistically-symmetric`
|===

`S` is optional whitespace. As in the MathML 4 intent grammar (section 5.1),
whitespace may stand before a property's `:`, between the head and `(`, and
around each argument, but not between `:` and the property name. `$unit` may
only be the last argument and refers to the unit content of the markup. The
concise marker still holds the absolute magnitude, so the meaning never
depends on digit alignment. Writers emit no whitespace, for example
`standard-uncertainty:concise(1.230,0.004)` or
`expanded-uncertainty(100.02147,0.00079,2,$unit)`.

Text that starts with one of the three names is a marker. A marker that does
not have exactly this shape (wrong argument count, a bad number, an unknown
property, `$unit` with no unit content) raises `InvalidUncertainty`; it is
never read as ordinary content. The reader is
`Plurimath::Mathml::UncertaintyMarker`, shared by the three formats.

=== AsciiMath

[source]
----
ustd(1.230, 0.004)                            standard, absolute
ustd(1.230(4))                                standard, concise
uexp(10.0, 0.3, 2)                            expanded
uexp(10.0, 0.3, 2, 0.95)                      expanded with p
ucov(1.024, 0.983, 1.088, 0.95, shortest)     coverage interval
uexp(100.02147, 0.00079, 2, "unitsml(g)")     with a unit, always last
----

AsciiMath has no marker: the call is the whole form. The grammar, shared
exponents, the fallback for malformed calls and the locale rule are in
link:asciimath.adoc#uncertainty[AsciiMath in Plurimath].

=== MathML

An `mrow` whose `intent` is the marker. The marker is written whatever the
`intent:` option of `to_mathml` is, because it carries data, not only speech
hints. The unit is an `mrow arg="unit"` inside it.

[source,xml]
----
<mrow intent="standard-uncertainty(1.230,0.004)">
  <mn>1.230</mn>
  <mrow>
    <mo>(</mo>
    <mn>0.004</mn>
    <mo>)</mo>
  </mrow>
</mrow>
----

An expanded result shows `(10.0 ± 0.3)` followed by `<mo>,</mo><mi>k</mi>`,
`<mo>=</mo><mn>2</mn>` and, with `p`, the same for `p`. A coverage interval
shows the value, a comma and the bracketed endpoints, then `p`. A reader that
ignores `intent` shows the visible form. More than one `arg="unit"` child
raises `InvalidUncertainty`.

=== OMML

OMML has no attribute for meaning. The marker is the text of a hidden,
zero-size phantom placed first inside an `m:box` that holds the whole result:

[source,xml]
----
<m:box>
  <m:e>
    <m:phant>
      <m:phantPr>
        <m:show m:val="off"/>
        <m:zeroWid m:val="on"/>
        <m:zeroAsc m:val="on"/>
        <m:zeroDesc m:val="on"/>
      </m:phantPr>
      <m:e>
        <m:r>
          <m:rPr>
            <m:sty m:val="p"/>
          </m:rPr>
          <m:t>standard-uncertainty(1.230,0.004)</m:t>
        </m:r>
      </m:e>
    </m:phant>
    <m:r>
      <m:t>1.230</m:t>
    </m:r>
    <m:d>
      <m:dPr>
        <m:begChr m:val="("/>
        <m:sepChr m:val=""/>
        <m:endChr m:val=")"/>
      </m:dPr>
      <m:e>
        <m:r>
          <m:t>0.004</m:t>
        </m:r>
      </m:e>
    </m:d>
  </m:e>
</m:box>
----

The visible content follows as one `m:r` per number and sign and an `m:d` per
bracket. A unit is the one inner `m:box` after it. A phantom counts as a
marker only when `m:show` is off. A hidden phantom whose runs spell a marker
but that also holds anything other than `m:r` runs, or a box with more than
one inner `m:box`, raises `InvalidUncertainty`.

=== UnicodeMath

The intent form `ⓘ("marker"visible)`, with the unit as `+ⓐ(unit ...)+`:

[source]
----
ⓘ("standard-uncertainty(1.230,0.004)"1.230(0.004))
ⓘ("standard-uncertainty:concise(1.230,0.004)"1.230(4))
ⓘ("expanded-uncertainty(10.0,0.3,2,0.95)"(10.0±0.3), k=2, p=0.95)
ⓘ("coverage-interval:shortest(1.024,0.983,1.088,0.95)"1.024, [0.983, 1.088], p=0.95)
ⓘ("expanded-uncertainty(100.02147,0.00079,2,$unit)"(100.02147±0.00079)ⓐ(unit \mupg), k=2)
----

A negative value that would start the visible content is put in the invisible
`〖〗` group, because the reader cannot take `+"marker"-...+`; the marker is
unchanged: `ⓘ("standard-uncertainty(-1.230,0.004)"〖-1.230〗(0.004))`. The
reader also accepts `±` with spaces around it.

=== LaTeX and HTML

Written only, in plain math with no package:

[cols="1,2,2"]
|===
| |LaTeX |HTML

|standard, absolute |`1.230(0.004)` |`1.230(0.004)`
|standard, concise |`1.230(4)` |`1.230(4)`
|expanded |`(10.0 \pm 0.3),\ k = 2` |`+(10.0 &#xb1; 0.3), k = 2+`
|expanded with `p` |`(10.0 \pm 0.3),\ k = 2,\ p = 0.95` |`+(10.0 &#xb1; 0.3), k = 2, p = 0.95+`
|coverage interval |`1.024,\ [0.983, 1.088],\ p = 0.95` |`1.024, [0.983, 1.088], p = 0.95`
|===

The interval choice is not shown. An expanded or interval result is never
written as a standard one, and a standard result is never written with `±`.
Reading this LaTeX back gives ordinary numbers and brackets, not an
uncertainty.

[[round-trip]]
== Round-trip matrix

Each row says what survives writing a node in a format and reading it back
with Plurimath. "Exact" means the node read back is `==` to the node written.

[cols="2,1,1,1,1,1,1"]
|===
| |AsciiMath |MathML |OMML |UnicodeMath |LaTeX |HTML

|value, magnitude, endpoints, `k`, `p` (exact text) |exact |exact |exact |exact |shown |shown
|category |exact |exact |exact |exact |by layout |by layout
|absolute or concise notation |exact |exact |exact |exact |shown |shown
|interval choice |exact |exact |exact |exact |lost |lost
|negative value |exact |exact |exact |exact |shown |shown
|unit |exact |rendered |rendered |rendered |shown |shown
|read back as `Uncertainty` |yes |yes |yes |yes |no |no
|===

"Rendered" means the unit comes back as its rendered `Math::Formula`, not as
a `Unitsml` node, so the node is not `==` to the one written, although its
other fields are. Written on to AsciiMath, such a unit becomes
`+"unitsml(...)"+` again when the rule in <<units>> allows it. Two cases do
not:

* units whose rendered symbols are not ASCII letters (`µm`, `°C`) are written
  after the call;
* in UnicodeMath, a multi-letter unit symbol written as `\mupkg` is read back
  as the upright `k` followed by `g`, so `kg` and `+kg·m^2+` are written to
  AsciiMath after the call (`ustd(1.2, 0.1) rm(k) g`). Units of one letter per
  symbol, such as `g` and `+m·s^-1+`, return as `+"unitsml(...)"+`.

Other software: a MathML consumer that ignores `intent` shows the visible
form. An OMML consumer that ignores hidden phantoms shows the marker text as
ordinary text. Word's handling of the phantom is not yet tested (see
<<open-decisions>>).

[[errors]]
== Errors

* `Plurimath::Errors::InvalidUncertainty`, a `Plurimath::Error`, is raised by
  the constructor and by the marker reader. Through `Plurimath::Math.parse`
  it reaches the caller as `Plurimath::Math::ParseError`, with no `cause`.
* `Plurimath::Math::AmbiguousDecimalError`, a `Plurimath::Math::ParseError`,
  is raised by the AsciiMath reader for a likely decimal comma in a call under
  a non-dot locale, and reaches the caller unchanged.
* A malformed AsciiMath call that does not match the call grammar is not an
  error; it reads as letters (see link:asciimath.adoc#uncertainty[AsciiMath
  in Plurimath]).

[[open-decisions]]
== Open decisions

These are not decided. Each links the issue where the decision belongs.

. *Coverage interval and the `+a/−b` layout.* The coverage-interval variant is
  implemented as above. The common `10.0^{+0.3}_{-0.2}` layout is not, because
  neither JCGM 100 nor JCGM 101 defines what its two numbers mean. Whether to
  support it, and with what meaning, is a maintainer decision
  (https://github.com/plurimath/plurimath/issues/524[#524],
  https://github.com/plurimath/plurimath/issues/493[#493]).
. *Inline `±` sugar.* Whether `(10.3 ± 0.2) cm` should read as an
  uncertainty at all, with which default category, and how `±` must be fenced.
  #524 recommends rejecting `+-` (ambiguous with `3 + (-1)`) and `pm`
  (picometre) (#524 item 4).
. *Shared exponent outside the calls.* `(3.85 +/- 0.23)e4` and `680(41)e-3`
  as bare forms depend on the `±` decision; the call forms already accept a
  shared exponent (#524 item 1,
  https://github.com/plurimath/amath/issues/13[amath#13]).
. *Relative notation*, `(10.3 +/- 2%) cm`, stored as an absolute magnitude
  (#524 item 2).
. *Distribution tags* for Type B input (`+~rect+`, `+~triang+`, `+~arcsine+`) as a
  structured field, never inferred from spelling (#524 item 3).
. *Concise form scope.* `10.3(2)` outside a call stays markup-only; in an
  evaluator language it would collide with function application (#524 item 5,
  https://github.com/plurimath/plurimath/issues/513[#513]).
. *Marker syntax against MathML 4.* The marker follows our reading of the
  MathML 4 intent grammar and has not been checked with a MathML 4 validator
  or screen reader (#524).
. *OMML phantom in Word.* Whether Word keeps the hidden zero-size phantom when
  the equation is edited, and how it displays it, is untested (#524).
. *Marker against visible content.* When the visible content disagrees with
  the marker, the reader trusts the marker without a warning. Raising an error
  instead is the alternative (#524).
. *Unit scoping.* One unit applies to the value and the uncertainty; an
  uncertainty is a difference quantity, so a unit conversion would apply the
  factor and never the offset. This matters once conversion exists (#524,
  #514).
. *LaTeX input.* Reading `siunitx` (`\num{1.230(4)}`) is a separate task
  (#524).
. *Where the AsciiMath call forms live.* They are implemented in the AsciiMath
  grammar and stay there. Moving them into the proposed dialect P ("pma") is
  tracked in https://github.com/plurimath/amath/issues/17[amath#17] and
  waits on https://github.com/plurimath/amath/issues/16[amath#16].
. *Closing #493.* All work planned in #493 is merged; the issue is still open.
